# 转发渠道对接指南

> 面向：**在管理后台配置渠道的人**。接口规格（请求体、错误码、签名算法）在代码里，
> 每个渠道一个 `ChannelSender` 实现，类的 javadoc 就是那份规格。
>
> ⚠️ 本文里的「去哪儿点」来自各平台公开文档与常见操作路径，**平台界面会改**。
> 如果找不到对应的入口，以各平台当期的官方文档为准；本文更可靠的部分是
> 「填进哪个字段」和「有哪些坑」—— 那些对应的是代码里的实现，不会漂。

---

## 0. 通用三步

**只建渠道不会有任何短信被转发。** 必须两步都做完：

```
① 转发渠道  建一个渠道 → 点「测试」确认能收到
② 转发规则  把渠道和短信条件关联起来
③ （可选）  转发渠道页看健康状态、投递记录页看「发出去了吗」
```

- 管理端路径：左侧菜单「转发渠道」/「转发规则」/「投递记录」
- **先点「测试」**：它会发一条样例消息（不含真实验证码）。这一步能省掉后面所有猜测 ——
  配错了立刻知道，而不是等真有短信时才发现
- 规则是**并集**语义：一条短信可以同时进「运维群」和「我的微信」，
  多条规则命中时渠道累加（不像采集规则那样首条命中即定论）

---

## ⚠️ 先说这一条

**转发出去的是短信原文，验证码不做任何处理。**

```
【备用机-1 · 10690300 · 09-20 10:30:00】
【某某】您的验证码是 483920，5 分钟内有效。
```

所以「**谁能看到这条消息**」= 「谁能用这个验证码**登录你的账号**」。

| 渠道 | 默认收件范围 |
| --- | --- |
| 企微/飞书/钉钉群机器人、Slack | **一整个群/频道** |
| Telegram、企业微信应用消息 | 可能是个人也可能是多个，看你怎么填 |
| WxPusher / Server酱 / PushPlus | **默认只推给你自己**（但填了主题/群组编码就变成广播） |

**只在收件范围里只有你自己的时候用转发。** 群里多一个人，你的每一个验证码都多一个使用者，
而且**运行时不会有任何提示**。

## 1. 企业微信群机器人

**推到**：一个企业微信群。**门槛最低** —— 一个 URL 即全部凭据，不需要企业主体、不需要签名。

### 拿凭据
1. 手机或桌面版企业微信 → 进入目标群 → 右上角群设置
2. 「群机器人」→ 添加机器人 → 新创建一个
3. 复制它给出的 **Webhook 地址**（形如 `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=xxxx`）

### 填什么
| 字段 | 填 |
| --- | --- |
| Webhook 地址 | 上面复制的那一整条 |

### 坑
- **这个地址就是全部凭证**。谁拿到它都能往这个群发消息。别贴到聊天记录、工单、截图里
- 只接受 `qyapi.weixin.qq.com` 的地址（代码里做了域名白名单），填别的会被拒
- 限流 20 条/分钟，是官方硬限

## 2. 飞书群机器人

**推到**：一个飞书群。

### 拿凭据
1. 群设置 → 群机器人 → 添加机器人 → **自定义机器人**
2. 复制 **Webhook 地址**（形如 `https://open.feishu.cn/open-apis/bot/v2/hook/xxxx`）
3. 安全设置里如果选「**签名校验**」，会再给你一个 **密钥**，一并复制

### 填什么
| 字段 | 填 |
| --- | --- |
| Webhook 地址 | 第 2 步的地址 |
| 加签密钥 | 第 3 步的密钥（安全设置没选签名就留空） |

### 坑
- **同一个机器人无法添加到多个群**。要给多个群转发，每个群单独建一个机器人
- 加签密钥与钉钉的**完全不同**（见下一节）
- 限流 100 次/分钟、5 次/秒；官方建议避开 10:00、17:30 这类整点/半点

## 3. 钉钉群机器人

**推到**：一个钉钉群。

### 拿凭据
1. 群设置 → 智能群助手 → 添加机器人 → **自定义**
2. **安全设置至少勾一项**，否则保存不了：
   - **加签**：会给你一个密钥 → 复制，填进「加签密钥」
   - **自定义关键词**：填 `短信转发`（见下面「坑」）
   - IP 白名单
3. 复制 **Webhook 地址**（形如 `https://oapi.dingtalk.com/robot/send?access_token=xxxx`）

### 填什么
| 字段 | 填 |
| --- | --- |
| Webhook 地址 | 第 3 步的地址 |
| 加签密钥 | 只有安全设置选「加签」时才填 |

### 坑
- **选「自定义关键词」方式时，关键词要填正文里本来就有的词**，比如 `验证码`。
  钉钉校验的是消息内容是否包含关键词，而转发的消息长这样：

  ```
  【备用机-1 · 10690300 · 09-20 10:30:00】
  【某某】您的验证码是 483920，5 分钟内有效。
  ```

  填 `短信转发` 是**匹配不上**的 —— 那四个字不在消息里（它们在钉钉机器人的
  markdown 标题字段上，那个字段是否参与关键词校验官方没说清，不要赌）。
  建议直接填 `验证码`，验证码短信基本都含这三个字。
  如果你转发的短信不一定含这三个字，**请改用「加签」** —— 加签也更安全。
- **Webhook 里的 `access_token` 是机器人的 token，不是应用的 access_token** ——
  官方专门强调过，是最常见的混淆点
- 加签的 `timestamp` 与 `sign` **必须拼在 URL 上**（飞书是放请求体，两家相反）。
  代码已经处理，你只要把密钥填对
- 限流 20 条/分钟，**超过会限流 10 分钟**（惩罚比企微重），所以默认只放 15 条/分钟

## 4. Telegram Bot

**推到**：你自己的 Telegram，或一个 Telegram 群。适合已经在用 Telegram 的人。

### 拿凭据
1. 在 Telegram 里找 **@BotFather** → 发 `/newbot` → 按提示建一个 bot
2. 它会给你一串 **Token**（形如 `123456:ABC-DEF...`）→ 复制
3. **给这个新建的 bot 发一条 `/start`**（关键，见「坑」）
4. 拿 chat_id：
   - 个人：找 **@userinfobot** 发消息，它会回你的 ID
   - 群：把 bot 拉进群，然后访问
     `https://api.telegram.org/bot<你的Token>/getUpdates`，在返回的 JSON 里找 `chat.id`（群是负数）

### 填什么
| 字段 | 填 |
| --- | --- |
| Bot Token | 第 2 步的 token |
| Chat ID | 第 4 步拿到的 id（群填负数） |

### 坑
- 🚨 **bot 不能主动私聊没跟它说过话的用户**，会返回 403。
  所以第 3 步不能省 —— 不先 `/start`，配好了也发不出去
- 限流：群 20 条/分钟；单 chat 还有 1 条/秒

2. 选目标频道 → 生成 Webhook URL（形如 `https://hooks.slack.com/services/T.../B.../xxxx`）
3. 复制

### 填什么
| 字段 | 填 |
| --- | --- |
| Webhook 地址 | 上面复制的 URL |

### 坑
- 🚨 **限流最严：1 条/秒**，官方警告「超限后继续发送可能导致应用被**永久禁用**」。

## 6. WxPusher（推到个人微信）

**推到**：**你自己的微信**。这是「转发到我的微信」最省事的路径，免费、**无每日条数上限**。

### 方式 A：SPT 极简模式（推荐，无需注册应用）
1. 打开 [wxpusher.zjiecode.com](https://wxpusher.zjiecode.com) → 微信扫码登录
2. 在「我的」→ 找到 **SPT**（极简推送的标识）
3. 复制那串 SPT

### 方式 B：标准模式
1. 同上登录 → 「应用管理」→ 创建应用 → 得到 **AppToken**（形如 `AT_xxx`）
2. 「用户管理」里能看到关注你应用的 **UID**（形如 `UID_xxx`）

### 填什么
| 字段 | 填 |
| --- | --- |
| SPT | 方式 A 的那串（**填了就走 SPT，下面的不用填**） |
| AppToken | 方式 B 的 AppToken |
| UID 列表 | 你自己的 UID，多个用逗号分隔 |
| 主题 ID | 留空。填了就是**一对多** |

### 坑
- **SPT 模式把内容放在 URL 里**，长短信会被截断。内容长的话用标准模式
- **只填自己的 UID 是推荐用法**。填了「主题 ID」就变成广播给关注该主题的所有人
- **SPT 泄漏后任何人都能给你发消息**。按凭据对待

## 8. PushPlus

**推到**：你自己的微信。

### 拿凭据
1. 打开 [pushplus.plus](https://www.pushplus.plus) → 微信扫码登录
2. 「一对一推送」里能看到你的 **Token** → 复制
3. （可选）「一对多推送」里创建群组，得到 **群组编码**

### 填什么
| 字段 | 填 |
| --- | --- |
| Token | 第 2 步的 Token |
| 群组编码 | 留空则只推给你自己。填了就是**一对多广播** |

### 坑
- 🚨 **这个接口是异步的**：返回成功只代表「请求已收到」，**不代表已经发出去**。
  所以投递记录里显示「成功」时，真实送达仍可能失败。这是接口本身的性质，
  要确认真实结果得去 PushPlus 后台看
- **失败的错误请求也计数** —— 额度会被失败的尝试吃掉
- 未实名 0 条；实名后 1 分钟 5 次 / 200 次/天

## 9. 通用 Webhook

**推到**：你自己搭的任意 HTTP 接口。用来对接公司内部系统，或接上面没覆盖的渠道。

### 拿凭据
自己准备一个能收 POST 的地址。

### 填什么
| 字段 | 填 |
| --- | --- |
| 目标地址 | 你的接口 URL |
| 签名密钥 | 可选。填了会在请求头带 HMAC-SHA256 签名（Standard Webhooks 规范） |
| 允许内网 | **对接内网服务时才打开**，默认关 |

### 发出去的请求

```json
{
  "text": "【备用机-1 · 10690300 · 09-20 10:30:00】\n【某某】您的验证码是 483920…",
  "sender": "10690300",
  "phone": "13800138000",
  "device": "备用机-1",
  "time": "09-20 10:30:00",
  "smsMessageId": 1024
}
```

**你只需要读 `text` 那一个字段。** 其余是附带的元信息。

填了签名密钥时，请求头会带（[Standard Webhooks](https://www.standardwebhooks.com/) 规范）：

```
webhook-id:        msg_xxxx
webhook-timestamp: 1758340000
webhook-signature: v1,<Base64(HMAC-SHA256(secret, "{id}.{timestamp}.{body}"))>
```

对端按同样规则验签即可。

### 坑
- ⚠️ **默认拦截内网地址**（回环、10/172.16/192.168、100.64、IPv6 唯一本地、云厂商元数据）。
  这是 SSRF 防护：管理后台账号一旦被盗，这个功能就是一个现成的内网探测器。
  对接内网服务时打开「允许内网」，并知道自己在做什么
- 成功判定是 **2xx**。3xx 算失败**且不跟随重定向** —— 跟随的话，SSRF 校验就白做了

## 10. 企业微信应用消息

**推到**：企业微信里的**个人**。比群机器人重得多（要企业主体、自建应用），
但如果公司已经在用企业微信，这是合规且可控的方案。

### 拿凭据
1. 登录 [企业微信管理后台](https://work.weixin.qq.com) → 「我的企业」→ 复制 **企业 ID**（形如 `ww...`）
2. 「应用管理」→ 自建 → 创建应用（记下 **AgentId** 与 **Secret**）
3. 在应用的「可见范围」里加上要接收消息的人

### 填什么
| 字段 | 填 |
| --- | --- |
| 企业 ID | 第 1 步的 CorpID |
| 应用密钥 | 第 2 步的 Secret |
| AgentId | 第 2 步的 AgentId |
| 接收人 | 接收者的企业微信账号；**留空则发给应用可见范围内的所有人** |

### 坑
- 🚨 **用的是「自建应用」的 Secret，不是「通讯录同步」的 Secret**。用错了会报
  `40001 invalid credential`
- **接收人必须在应用的「可见范围」里**，否则会返回 `invaliduser` —— 而且更坑的是：
  这时**接口仍然返回成功**，只是那个字段告诉你有人没收到。投递记录里会显示成失败并写明
  「部分成员未收到」，看到这条要去检查可见范围
- 如果没有「基础接口许可」（收费项），会返回 `unlicenseduser`，同样发不出去
- 限流：每应用对**同一个成员**不超过 30 次/分钟

## 出问题了怎么查

**管理后台 →「投递记录」**。每条记录带：状态、尝试次数、下次重试时间、对端状态码、
**脱敏后**的失败原因。列表和错误信息里的 webhook 地址都是打码的，不会泄漏凭据。

### 状态含义

| 状态 | 含义 | 要做什么 |
| --- | --- | --- |
| 待投递 | 排队中，或被限流推迟 | 等。积压一直涨说明渠道卡住了 |
| 发送中 | 正在发 | 卡在这一步超过 2 分钟会被自动回收重发 |
| 成功 | 发出去了 | —— |
| 失败（会重试） | 这次没成功，会按退避重试 | 等，或看失败原因 |
| **已放弃** | 重试用尽或遇到不可重试的错误 | **需要人介入**。点「重投」重新排入队列 |
| 已取消 | 所属渠道被停用，这条不再投递 | 不用管。重新启用渠道后新收到的短信会继续投递，**已取消的不会补发** |

> **停用渠道会顺手清掉它的积压。** 那些验证码早就过期了，重新启用时一次性补发出去
> 只是噪声。所以停用时会把还没发出去的记录置为「已取消」，而不是留着 —— 留着既没用，
> 又会一直显示成「待投递 + 下次重试」，读起来像马上要发出去。
>
> 渠道**连续失败到阈值自动停用**时也一样：调度器每分钟扫一次，把停用渠道下的未投递
> 记录收掉。

### 常见失败与对策

| 失败信息 / 错误码 | 原因 | 怎么办 |
| --- | --- | --- |
| `ConnectException` / 超时 | 网络不通 | 检查地址与网络；会自动重试 |
| HTTP 401 / 403 | 凭据无效 | 重新拿一次凭据 |
| 飞书 `19021` / 钉钉 `310000` | 签名失败 | 检查「加签密钥」是否填对、是否复制全 |
| 飞书 `19022` | IP 不在白名单 | 机器人安全设置里加了 IP 白名单，把服务器出口 IP 加进去或改用加签 |
| 飞书 `19024` | 关键词未命中 | 机器人用了「自定义关键词」方式，改用加签 |
| 企微 `40001` / `40013` | 企业 ID 或密钥不对 | 检查用的是不是**自建应用**的 Secret |
| 企微 `invaliduser` / `unlicenseduser` | 接收人不在应用可见范围 / 无接口许可 | 去企业微信后台把接收人加进可见范围 |
| Telegram 403 | bot 没被 `/start` 过 | 先给 bot 发一条 `/start` |
| Telegram 429 | 触发限流 | 会自动重试（至少等 30 秒） |
| Slack `no_active_hooks` | 钩子被删了 | 渠道会被**自动停用**，重新创建 |
| HTTP 410 Gone | 对端已经删了这个钩子 | 同上 |
| 目标解析到内网/保留地址 | SSRF 拦截 | 确实是内网服务就打开「允许内网」 |
| 渠道配置解密失败 | 加密密钥换过了 | 渠道的 webhook 地址要**重新填一遍** |

### 渠道被自动停用

连续失败 10 次会自动停用并在日志里报一声（`【转发渠道已自动停用】`）。
这是刻意的：一个持续失败的渠道每分钟都在朝对端打无效请求，而 Slack 这类对端
「超限后继续发送可能导致应用被永久禁用」。停下来让人看一眼，比继续撞下去好。

修好之后到「转发渠道」页手动启用 —— 重新启用会把连续失败计数清零。

## 加密密钥

渠道凭据（webhook 地址）在数据库里是**加密存储**的，密钥来自环境变量
`NOTIFY_ENCRYPT_KEY`。生成方式：

```bash
openssl rand -base64 32
```

**这个密钥丢了，所有渠道的凭据都要重新填一遍** —— 密文在库里，没有密钥读不出来。
建议和数据库密码一样对待（密码管理器 / K8s Secret）。

没配这个密钥时后端**照常启动**，只是转发不可启用 —— 一个可选能力不该成为整个应用的
启动依赖。你在「转发渠道」页会看到一条提示告诉你去配；打开转发总开关时也会被拦下来
并说明该设什么。配了但格式不对（不是合法的 Base64、或长度不是 32 字节）则会**拒绝启动**：
那是明确的配置错误，不该被静默降级成「功能没反应」。

| 分组 | 配置项 | 说明 |
| --- | --- | --- |
| 消息转发 | 消息转发 | 总开关。没配加密密钥时点开会报错并告诉你去设哪个变量 |
| | 消息里附带来源信息 | 转发时加不加「设备 · 发送方 · 时间」那一行 |
| | 转发轮询间隔 | 投递延迟主要由它决定 |
| | 渠道失败阈值 | 连续失败多少次后自动停用渠道 |
| 短信数据 | 短信保留天数 | 0 = 不清理。设大于 0 后每天按批删除更早的记录 |
| | 清理执行时间 | 每天几点清理 |
| 安全与会话 | 管理后台登录有效期 | 改完只对之后登录的人生效（已登录会话的过期时间签发时就定了） |
| | API Key 校验缓存 | 改大减轻数据库压力，但禁用密钥后的生效会变慢 |

判断一项配置该放哪边的标准只有一条：**密钥留环境变量，运行期策略进数据库**。

- **密钥一律在环境变量里**（`NOTIFY_ENCRYPT_KEY`、`APP_SECRET_KEY`…）。
  加密密钥尤其不能进库 —— 用库里的密钥去解库里的密文是**循环依赖**。
- **引导类配置**（管理员初始密码、数据源）只在启动那一刻有意义，也在环境变量里。
- 剩下那些**运维过程中会想调、调完想立刻看到效果的**，都在「系统设置」页。

## 附：故障告警发到哪个渠道？

告警（设备离线 / 转发渠道被自动停用 / 远程指令失败）走的是**同一套投递链路**，
但**规则是另一张表**：「告警规则」页，不是「转发规则」页。

| | 转发规则 | 告警规则 |
| --- | --- | --- |
| 决定什么 | 哪些**短信**发过去 | 什么**坏了**通知谁 |
| 匹配维度 | 发送方 / 正文关键词 / 接收号码 / 设备 | 告警类型 / 设备 |
| 在哪儿配 | 管理后台「转发规则」 | 管理后台「告警规则」 |

三条要点：

1. **必须至少配一个渠道**，否则那条规则永远不会发出任何东西 —— 服务端会拒绝保存，
   因为「配了但没生效」在列表上看起来和正常规则一模一样。
2. **空态里有个「一键创建三条默认规则」**：建库时**不种子化**告警规则，理由是种子数据的
   `channelIds` 必然为空，而后端会直接拒绝一条没有渠道的规则 —— 种子只能种出三条
   「无目标」的红标签。转发规则当初没种子化，也是同一个理由。
3. **渠道被自动停用时，告警会排除刚死掉的那个渠道**（它发不出去了），走剩下的渠道；
   一个都不剩就记一条 `ALERT_UNDELIVERABLE`（ERROR 级）。所以「只剩一个渠道」时，
   「渠道挂了」这件事是收不到通知的 —— 只在运行日志里看得到。**至少配两个渠道互为备份。**
